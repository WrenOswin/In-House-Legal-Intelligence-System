Phase 3

Rhetorical Role Prediction (RR) - 12 to 16 Oct 2026 (deadline 16 Oct 23:59 IST)


==========================================================================================
PHASE 3 SUMMARY - one rhetorical-role label per sentence, 13 labels, macro-F1
==========================================================================================
Task: for each test document (CL + IT domains), predict one label per sentence, same order and count.
Rules: start from the Phase-1 models (ALL FOUR architectures); >= 4 substantially different
experiments: >= 3 different fine-tuning/PEFT techniques (LoRMA compulsory) + >= 1 knowledge
distillation. Minimum 4 valid submissions (aim for 7-8).
Plan: Phase3_Plan.md. Hardware: same laptop (RTX 5070 Ti 12 GB), .venv kernel.

  R6  A d560 (58M)      knowledge distillation from R2 (or the R7 ensemble)

4. OBSERVATIONS
------------------------------------------------------------------------------------------
1. Labels come in long runs: 93.7% of CL and 75.4% of IT sentences share the previous sentence's
   label -> document context + a transition model (CRF/Viterbi) should matter most.

2. Rare labels: Issue (17 in CL), PrecedentOverruled (3, one IT doc), Dissent (284 but only 2 CL docs);
   Dissent and PrecOverruled are absent from dev. How Codabench's macro-F1 treats labels absent from
   gold is unknown -> local scorer reports both (all 13 labels / labels in gold+pred).

3. Dev and test are 10 docs each -> expect at least the +-0.03 noise seen in Phase 2.

4. The "previous gold label" oracle reaches macro-F1 0.754 / acc 0.884 on dev: most of the task is finding
   where a run of one role ends. Its weak labels are exactly the short-run ones: Issue 0.20, None 0.52,
   RulingByPresentCourt 0.57. -> a CRF/BiGRU over sentences is essential; the rare short-run roles decide macro-F1.

5. "all-13" macro-F1 is much lower than "present" (0.638 vs 0.754 for the oracle) because Dissent and
   PrecedentOverruled are absent from dev and count as F1 = 0. Which variant Codabench uses matters.

6. First runs: LoRMA (1.4% of A's weights trained) matches full fine-tuning on dev (0.566 vs 0.558; within the
   +-0.03 noise), as in Phase 2. Phase-1 ranking: A (0.56-0.57) > D (0.484) ~ C (0.481) > B (0.42)
   (Phase 1: A > D > C > B; D and C are tied here, within noise).
   R1 and R4 were still improving at the last epoch (15) -> a longer schedule may help them.
7. Full FT overfits fastest: train loss 0.05 by epoch 8, dev F1 jumps +-0.06 between epochs after that.

9. Codabench most likely averages over ALL 13 labels (or the test set also lacks some rare labels): dev
   all-13 tracks the test score with no bias (mean +0.005), while dev "present" overestimates by 0.074 on
   average. -> select models on dev all-13 from now on. Not proof: the test gold is hidden.

10. Dev barely predicts test here: rank correlation 0.31, single runs differ by up to 0.085 (R5). With 10
    test docs (5 per domain) one or two documents move the score a lot. Only large dev gaps mean anything.

11. D + prefix tuning is the best Codabench model (0.495), although it was 4th on dev. D is the only model
    with a 2048-token window, so each sentence sees about twice as much surrounding text; the test docs
    are longer than dev (IT test median 159 sentences / 6.6k words vs 120 / 3.7k in dev). Plausible
    reason, not tested yet.

12. LoRMA beats full fine-tuning on the test set again (0.450 vs 0.415), as in Phase 2 (0.509 vs 0.479).
    The KD student (58M, 0.455) also beats its own 140M teacher (R2, 0.415) on test.

13. Ensembling all six adds only +0.003 on dev, unlike Phase 2 (+0.04): the models make similar mistakes.

14. Round 2 (dev all-13): (a) context length on D: 2048 vs 1024 window 0.449 vs 0.439 - same within noise;
    (b) LoRMA on D (0.449) beats prefix tuning on D (R5 0.410) on dev, but R5 won on test;
    (c) longer training crops (128 sentences) did not help prefix tuning (0.418 vs 0.410);
    (d) R1 with a 20-epoch schedule stopped at epoch 7 with 0.449, worse than R1 (0.479): the slower LR decay
        changes the run, and patience on a noisy 10-doc dev set stops it early;
    (e) KD helps: the same 58M student scores 0.431 alone vs 0.465 with the teacher (+0.034), the same size
        of gain as in Phase 2 (+0.026).
    (f) ensembles do not beat the best single model on dev (all ten 0.475 vs R1 0.479).

15. Codabench round 2: the long-context explanation for R5 is NOT supported - D at 1024 tokens scored
    0.454 vs 0.444 at 2048. Four D runs differing in method/window span 0.422-0.495 and all 11 single
    models 0.443 +- 0.033 -> R5's 0.495 is partly a lucky draw on 10 test docs.
16. KD on the test set: student alone 0.466 vs with KD 0.455 - the opposite of dev (+0.034). Both gaps are
    inside the +-0.033 noise: KD's effect cannot be resolved with 10 dev / 10 test docs. Report both.
17. all10 ensemble 0.474: among the best and the least dependent on luck (averages 10 runs); the D-only
    ensemble (0.431) was worse than its members' mean (0.453).

18. Training on train+dev did NOT help: R5 0.495 -> 0.398, KD baseline 0.466 -> 0.423, R1 0.450 -> 0.468.
    Same config, 10 more docs, swings of -0.10 to +0.02: run-to-run randomness (+-0.05 on 10 test docs)
    dominates any effect of 12% more data. R5's 0.495 was largely luck.

19. Error analysis of the all10 ensemble on dev (per label, gold vs predicted counts):
    RatioOfTheDecision over-predicted (710 pred / 403 gold, F1 0.64); rare roles under-predicted:
    RulingByLowerCourt 26/102 (F1 0.41), None 13/33 (0.39), Issue 6/15 (0.48), ArgumentPetitioner 210/400.
    Top confusions (gold -> pred): ArgPet -> ArgResp 103, Fact -> Ratio 83, PrecRelied -> Ratio 80,
    ArgPet -> Ratio 71, PrecRelied -> Fact 43. Dissent / PrecOverruled are never predicted.
    -> the models fall back on the majority role; macro-F1 punishes that.

20. Logit adjustment (tau = 0.5) raises dev all-13 by ~+0.01 for the ensemble and +0.007 on average for
    single models, with a flat optimum 0.25-0.5 -> one parameter, small and consistent gain.

21. Logit adjustment did not carry over to the test set: -0.009 on average over 4 submissions (dev
    predicted +0.01). Like every other change in rounds 2-4, the effect is smaller than the +-0.03-0.05
    test noise. Conclusion for the report: with 10 dev / 10 test documents, differences below ~0.05
    between Phase-3 systems cannot be resolved; only the architecture gap (A/D/C ~0.44-0.47 vs B 0.36)
    and the PEFT ~ full-FT parity (repeated in Phase 2) are consistent findings.

22. From-scratch check (2026-10-13, TA requirement from Phase 3): every adaptation technique (LoRA, rsLoRA,
    LoRMA, IA3, prefix tuning, adapters, partial FT), KD, CRF/Viterbi and the head are written by hand in
    Phase3\src. Imports are only torch, numpy, regex (tokenizer) and the standard library; HF peft /
    transformers are not installed or used. (src\peft.py is our own file - same name as the HF library.)

8. KD: the 58M student reaches 0.549 vs the 140M teacher's 0.558 (98% of the score, 41% of the parameters,
   4.0 vs 5.4 GB training memory). The student WITHOUT KD has not been trained yet -> needed to show what the
   distillation itself adds (Phase 2: +0.026 on val).

- 2026-10-12 R5 (D + prefix tuning) crashed the laptop twice (Windows bugcheck 0x20001 + unexpected reboot,
  13:01 and ~13:06, both inside R5's first epoch; R6 was never reached). Cause: the first prefix-tuning version
  replaced D's blocked sliding-window kernel with a dense [T, T+P] mask (T = 2048) in all 8 layers.
  Fixes:
    peft._sliding_window_prefix: prefix keys/values added to each block of D's own blocked kernel
      (O(T*(2W+P)) memory); identical output to the dense version (max abs diff 5e-16, float64 test).
    train_rr: vram_fraction=0.75 (torch.cuda.set_per_process_memory_fraction -> an OOM error instead of
      Windows spilling into shared RAM), token_budget 8192 -> 4096, optional step_pause (s of idle GPU
      after each optimizer step; 0.2 for R5/R6). None of these are part of the run id (no effect on results
      except token_budget batching).
  Measured after the fix (25 steps on the densest docs + 1 dev pass): D prefix peak 3.43 GB, A d560 full 4.04 GB
  (R1/R2 ran at ~5.3 GB without problems).
