PHASE 5 SUMMARY - multi-label statute IDs per case document, macro-F1
==========================================================================================
Task: predict the set of applicable statute IDs (0-99) for each test document.
Metrics: macro-F1 (primary), micro-F1, subset accuracy. Output: [{"id": ..., "pred": [int, ...]}, ...],
one object per test doc, unique valid IDs only.
Rules (capstone doc section 11.2): start from the Phase-1 models (ALL FOUR architectures); >= 4 substantially
different experiments: >= 3 different fine-tuning/PEFT techniques (LoRMA compulsory) + >= 1 knowledge
distillation (larger teacher -> smaller student). Minimum 6 valid submissions (README).

2. DATA ANALYSIS (2026-10-18)
------------------------------------------------------------------------------------------
Sizes and fields
  train 42,750 docs (id, text, labels) | dev 10,181 (id, text, labels) | test 13,019 (id, text - NO labels)
  All ids unique, no empty texts, labels are ints. 3 train / 1 dev docs repeat a label inside the list
  (dedupe when building targets).

Document length (whitespace words)
            p10   median   p90    p99     max      mean
  train      90     430   2,766  8,143   86,858   1,124
  dev        90     543   2,957  8,856   69,230   1,249
  test       94     532   2,813  8,308  134,848   1,212
  Much shorter than CJPE (median ~3.5k BPE tokens there): the median doc fits in ~1-2 512-token chunks,
  but the p90 doc needs ~8 chunks. Long tail -> keep chunking + pooling from Phase 4.

Labels
  Exactly 100 statute IDs (0-99), all present in both train and dev (no unseen labels, no gaps).
  Labels per doc: mean 3.7 (train) / 3.9 (dev), median 3, p90 7, max 31. 21% of train docs have 1 label.
  Frequency: from 11,731 train docs (ID 5) down to 272 (ID 84). NOT extremely long-tailed: the rarest label
  still has 272 train / 68 dev docs; 30 labels have <= 500 train docs. Top 10 labels = 41% of label mass,
  top 20 = 60%. Dev frequencies are ~0.25x train for every label (stratified split) - dev is a reliable
  macro-F1 proxy (>= 68 positives per label), unlike Phase 3.
  Most frequent: 5 (11.7k), 34 (10.4k), 97 (7.9k), 43 (7.7k), 39 (7.1k), 12, 13, 10, 77, 94.
  Co-occurrence is strong: (5,34) 3.6k, (12,13) 3.5k, (43,97) 3.4k, (5,43) 3.3k, (13,14) 2.8k;
  16,191 distinct label sets in train; most common sets {34}, {5}, {61}, {5,34}, {39}, {20,28}.
  -> label correlation worth exploiting (e.g. a co-occurrence-aware head or label-pair post-processing).

Masking (important for modelling)
  Statute references in the text are replaced by <SECTION> and <ACT> (5.3 of each per train doc on average);
  parties/names by <ENTITY> (~56-62 per doc). 4,260 train / 1,208 test docs have no <SECTION>/<ACT> at all.
  Unmasked leftovers exist but are rare: "section/sec./s./article/rule + number" in 2.8% of train, 3.7% of
  dev, 3.8% of test docs; "Penal Code / IPC / CrPC / Evidence Act" named in 1.7% of train docs.
  -> The model must infer statutes from facts and context (offence descriptions, procedure), not read them
  off the text. The context around <SECTION>/<ACT> masks is a natural "targeted context selection" signal.
  Phase-1 tokenizer: add/handle <SECTION>, <ACT>, <ENTITY> as single tokens (check how Phase-1 BPE splits them).
  Texts also contain glued words ("theprosecution", "proceedingmay") from PDF extraction.

Overlap / leak check
  No shared ids between any splits. test.json has no labels -> NO test-label leak this phase (unlike Phase 4).
  Exact duplicate texts (whitespace/case normalised):
    within train 435, within dev 63, within test 80
    train-dev 81, train-test 109, dev-test 62 identical texts
  Duplicates are mostly short boilerplate orders (median 275 words; test-side duplicates median 59 words,
  e.g. "Accordingly, the prayer for anticipatory bail is rejected..."). Among labelled duplicate groups
  (train+dev) only 234/335 have identical label sets; for docs > 200 words 174/179 agree, for short boiler-
  plate they often disagree -> label noise on short docs.
  192 test docs have an exact labelled duplicate in train/dev; ~4% of a 1,000-doc test sample has a near-
  duplicate (> 80% 8-gram containment) in train+dev. Using train/dev labels for those is just using the
  provided training data (not a leak), but a nearest-neighbour lookup should only be trusted for long docs.
  For honest dev scores: train-dev share 81 identical texts -> drop them from dev (or from train) when
  measuring dev F1, otherwise dev is slightly optimistic.

  KD with cached teacher logits) with a 100-way sigmoid head + BCE (try class-balanced / focal / ASL loss).
